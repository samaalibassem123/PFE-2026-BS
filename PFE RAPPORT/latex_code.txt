\chapter{General Introduction}
\section{General Context of the Project}
This chapter introduces the organizational context of the internship, defines the problem this project aims to solve, establishes system requirements, and justifies the selected development methodology.

\section{Company Presentation}
The internship was carried out within a company that manages a significant workforce distributed across multiple projects. The organization relies on digital tools to administer human resources, project assignments, and employee scheduling. Two existing systems --- BioTime and EasyProject --- were already in place, each serving a distinct operational purpose.

\subsection{Existing Information Systems}
The company operates two independent database systems:
\begin{itemize}[noitemsep]
    \item \textbf{BioTime (PostgreSQL)}: Connected to ZKTeco biometric devices, recording raw clock-in and clock-out events with employee identifiers and timestamps.
    \item \textbf{EasyProject (MySQL)}: Handles employee profiles, team structure, project assignments, schedules, and leave requests.
\end{itemize}

These systems operate in silos with no native integration, which creates visibility gaps and forces manual reconciliation.

\section{Problem Statement}
\subsection{Identified Pain Points}
Prior to this project, the company faced the following operational challenges:
\begin{itemize}[noitemsep]
    \item Data silos between attendance data (BioTime/PostgreSQL) and HR/project data (EasyProject/MySQL).
    \item No unified view combining physical attendance and project assignment.
    \item Conflict risks between systems (presence/absence mismatches and overlapping assignments).
    \item No real-time monitoring dashboard for managers.
    \item Manual, time-consuming, and error-prone Excel reporting.
    \item No unified role-based authentication layer across the whole workflow.
\end{itemize}

\subsection{Project Objective}
The objective of this internship project is to design and implement a unified web application that:
\begin{itemize}[noitemsep]
    \item Merges BioTime and EasyProject into a conflict-free PostgreSQL database through an ETL pipeline.
    \item Exposes secure and role-aware REST APIs using FastAPI.
    \item Provides a React dashboard for real-time attendance, leave, delay, overtime, and assignment visualization.
    \item Eliminates data conflicts through ETL transformation and reconciliation rules.
\end{itemize}

\section{Development Methodology: Scrum}
\subsection{Why Scrum Was Chosen}
\subsubsection{(a) Evolving and partially unknown requirements}
At the start of the internship, the complete conflict-resolution logic between BioTime and EasyProject was not fully understood. Scrum enabled progressive refinement after each sprint.

\subsubsection{(b) Short internship duration (3 months)}
With a fixed 12-week timeline, two-week sprints ensured continuous delivery of working increments rather than a risky end-only delivery.

\subsubsection{(c) Modular and layered architecture}
The project naturally decomposes into ETL/data, API/backend, and UI/frontend layers. Scrum sprint boundaries map cleanly onto this layered architecture.

\subsubsection{(d) Adaptability to technical challenges}
Data quality issues such as missing IDs, timestamp mismatch, and null values were addressed iteratively through sprint planning and retrospectives.

\subsubsection{(e) Why not Waterfall?}
Waterfall requires complete and stable upfront requirements, which was not realistic for this data-integration project under internship time constraints.

\subsubsection{(f) Why not Kanban alone?}
Kanban is useful for continuous flow but lacks the strong time-boxed cadence required for milestone tracking in a fixed-duration internship.

\subsection{Scrum Framework Overview}
\subsubsection{Roles}
\begin{itemize}[noitemsep]

    \item Scrum Master / Developer: intern.

\subsubsection{Artifacts}

\subsection{Authentication Workflow}

This subsection presents the authentication sequence diagram as a PNG export.

\textbf{Authentication flow logic:}
\begin{itemize}[noitemsep]
    \item \textbf{Login flow with JWT}: The user submits credentials; the backend validates them and issues a signed JWT access token with an expiration time.
    \item \textbf{Access to protected routes}: The client sends the JWT in the \texttt{Authorization: Bearer <token>} header; the backend verifies signature, claims, and role permissions before granting access.
    \item \textbf{Token expiration}: When the token reaches its \texttt{exp} timestamp, protected requests are rejected (unauthorized), and the user must re-authenticate (or use a refresh strategy if implemented).
    \item \textbf{User logout}: On logout, the client removes stored token(s). If server-side revocation or blacklisting is enabled, the token is invalidated immediately.
\end{itemize}

\section{Global System Architecture}

The global architecture starts by extracting data from \textbf{BioTime (PostgreSQL)} and \textbf{EasyProject (MySQL)} with \textbf{SQLAlchemy}. Then, the data is transformed and loaded into the main application database.

On top of this unified database, the backend is implemented with \textbf{FastAPI}, \textbf{Alembic}, and \textbf{SQLAlchemy} to expose endpoints consumed by a frontend built with \textbf{React}, \textbf{Tailwind CSS}, and \textbf{shadcn/ui}.
