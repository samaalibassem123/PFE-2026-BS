# Comprehensive Project Report: PFE-2026-BS

This document serves as a detailed prompt outlining the specific architecture and functionality of the "PFE-2026-BS" project. This project is a Full-Stack modern web application (React, FastAPI, PostgreSQL) designed for internal Human Resources, employee time & attendance tracking, and project management capabilities.

The report should use the following chapters, each corresponding to a core software module present in both the frontend (`src/modules`) and backend (`app/modules`) repositories.

---

## Chapter 1: Authentication Module (`auth`)
**Purpose:** Secures the platform and manages user sessions.
- **Backend Responsibilities:** Handles login endpoints, validates credentials against the PostgreSQL database, generates stateless JWT (JSON Web Tokens) for session management, and uses bcrypt/argon2 hashing. Provides role-based access control (Admin, HR, Project Manager).
- **Frontend Responsibilities:** Handles login forms, auth state context, secure cookie/local storage management for tokens, and protected route wrappers to prevent unauthorized access.

## Chapter 2: Dashboard Module (`dashboard`)
**Purpose:** Provides a high-level, aggregate view of organizational data.
- **Frontend Responsibilities:** Acts as the primary landing page upon authentication. Visualizes key metrics like active projects, employee count, and daily attendance summaries using charts (`recharts`) and modern 3D UI designs (using `three` and `vanta`). *(Note: Primarly a frontend aggregation module).*

## Chapter 3: User Management Module (`user` & `pending_users`)
**Purpose:** Administration of platform access and user lifecycle.
- **Responsibilities:** Allows administrators to view, create, and manage actual platform users (as distinct from employees). The `pending-users` sub-module handles workflows for approving new user registrations or access requests before they are fully active in the system.

## Chapter 4: Projects Module (`projects`)
**Purpose:** Core entity management for company initiatives.
- **Responsibilities:** Handles CRUD operations for Projects. Tracks metadata such as `name`, `identifier`, and lifecycle dates. This module allows HR and Admins to define the project landscape of the organization.

## Chapter 5: Employees Module (`employees`)
**Purpose:** Central repository for human resources data.
- **Responsibilities:** Manages the personnel directory. It links to the `departments` table (via database keys), storing `emp_full_name`, `email`, and `hire_date`. Backend endpoints serve paginated employee lists to the frontend data tables (`@tanstack/react-table`). It interfaces with SQL views like `biotime_employee_view` to stay synchronized with biometric hardware records.

## Chapter 6: Project Members Allocation (`members`)
**Purpose:** Connects human resources to operational work.
- **Responsibilities:** Specifically manages the Many-to-Many relationship between `projects` and `employees`. This module allows Project Managers to assign staff to specific projects, dynamically allocating human capital across the organization.

## Chapter 7: Daily Timecard Module (`checkinout`)
**Purpose:** Granular tracking of daily physical presence.
- **Responsibilities:** Corresponds to the `attendance` tables and `check_in_out_view`. This module pulls data (typically generated by biometric devices) representing explicit daily `check_in` and `check_out` timestamps. It categorizes the data by date and weekday.

## Chapter 8: Employee Leave Applications (`employees_leave`)
**Purpose:** Management of out-of-office workflows.
- **Responsibilities:** Handles requests for time off. Interfaces with the `biotime_att_leave_view` to provide data regarding `start_time`, `end_time`, `apply_reason`, and the approval workflows associated with the leave (e.g., who approved it and when) tied to distinct pay codes.

## Chapter 9: Member Attendance Tracking (`members_attendance` / `members-att`)
**Purpose:** Correlating time tracking with project allocation.
- **Responsibilities:** Focuses on the `employee_attendance_event` workflows. Unlike the raw daily check-in, this module tracks specific macro-events (like remote work allocations or specific assignment blocks) tied to the employees allocated as members on the platform.
